# Vertical Product MVP acceptance

## Automated acceptance

- The Product Host validates the ordered native registry containing `watch-design-kernel` and `tablet-design-kernel`.
- Registry contracts prove that ordinary Skills do not participate in vertical mutual exclusion.
- Completed successful native vertical `Skill` loads project into the existing Composer selection; unsuccessful, incomplete, and ordinary Skill loads do not.
- Session-scope contracts preserve the selected vertical across local refresh/reopen without binding another Project.
- The journey covers native Project/Session resume, generic Artifact projection, Asset-to-Chat reference identity, and full native Canvas round-trip context for both registered verticals.
- Web tests never call a text or image Provider.
- Watch and Tablet Kernel validators check Design Dialogue options, the 3–6-card range, visible `userConstraints`, immutable knowledge evidence, BaseModel completeness, and package integrity.
- `NativeJarvisApp` imports no Product registry or vertical package; Professional Workspace remains a separate deletion-safe entry.

## Known demo limits

- The shared Agent Workspace brand is independent of verticals; only the Composer Skill identity changes.
- Customer permissions, tenancy, deployment isolation, and per-customer vertical exposure remain deferred.
- Selected vertical preference uses the existing local Chat Session scope; cross-device preference persistence is deferred.
- Concept Sketch is Tablet's first acceptance-backed executable target. The other eight targets currently provide packaged professional guidance rather than dedicated Runtime paths.
- Artifact Card enhancement still requires stable native asset identity plus a matching Canvas node; otherwise it falls back to the native thumbnail.
- No runtime plugin marketplace, frontend category classifier, vertical database table, custom Canvas node type, or vertical lifecycle callback is introduced.
