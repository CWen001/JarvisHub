# Activate recognized vertical Skills without narrowing Jarvis

Watch, Tablet, and future supported design capabilities coexist as native Vertical Skill Packages. The Product Host keeps only an ordered registry of the native Skill keys that count as mutually exclusive verticals; a package's Skill frontmatter supplies its runtime identity, while BaseModels, professional references, quality standards, process guidance, manifests, and validators remain inside the package. The shared Agent Workspace brand is independent of every vertical, and the former per-vertical Web brand descriptor is removed.

The user does not preselect a category and Projects carry no vertical binding. Jarvis's real native `Skill` load is the authority for automatic recognition: the existing Chat Adapter observes completed successful loads of registered vertical Skills and projects the latest one through the existing Composer `selectedSkill`. Loading another registered vertical replaces it; ordinary native Skills remain independently available for phase-specific work and never participate in this registry. The frontend performs no competing keyword classification.

No new public Vertical Activation Runtime or activate/close/switch/restore methods are introduced. Agent Workspace continues to use its existing deep Runtime Interface—`getSnapshot`, `subscribe`, and `dispatch`—and its existing `chat.select-skill` intent. Manual selection supplies the selected vertical as a required Skill, closing supplies `null`, and automatic native loads converge through the same existing selected-Skill state. The current selection is stored in the existing Chat tab Session scope so refresh and local Session reopening restore it without a Project binding or a new backend state system; Jarvis-native Skill traces and generation evidence remain execution authority. Cross-device Session preference storage is deferred until a real deployment requirement exists.

The active vertical has contextual inertia: ambiguous category-neutral follow-ups continue under it, a clearly identified different category replaces it visibly, and a conflicting but ambiguous request should trigger one concise clarification rather than speculative switching. A manual close suppresses accidental ambiguous continuation; an explicit later request or manual selection may reactivate the vertical. With no selected vertical, Jarvis retains its complete general design and execution capability. This rejects hidden one-turn loading, optional compliance after recognition, per-vertical Composer logic, callback-heavy plugin descriptors, permanently locked Projects or Sessions, speculative frontend classification, and vertical packages that replace or artificially restrict Jarvis's broader capabilities.
